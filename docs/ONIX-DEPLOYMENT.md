# Minecraft на ONIXPC

Целевая схема использует прежние Paper, Velocity и PostgreSQL в Docker Compose.
Миры и конфигурация находятся на `M:\Services\agicraftmc`, операционные файлы —
в `M:\Services\agicraft-onix-ops`. Файлы с секретами не входят в Git.

## Сетевой вход

Docker Desktop скрывает исходный адрес входящего соединения. Нативный
`scripts/onix_game_proxy.py` принимает Java TCP на порту 25565 и передаёт его
на локальный порт 25566 с PROXY protocol v1. В Velocity включается
`haproxy-protocol`. Порт 25566 публикуется только на 127.0.0.1.

Для Bedrock мост принимает UDP на порту 19132, передаёт пакеты на локальный
порт 19133 с PROXY protocol v2. В Geyser включается соответствующая настройка
в секции `advanced.bedrock`; его Java-интеграция также учитывает режим Velocity.
Порт 19133 не публикуется на внешнем интерфейсе.

Входящий PROXY-заголовок принимается только от явно доверенного предыдущего
узла. Обычный клиент не может подставить себе чужой IP. Мост сохраняет отдельный
обратный UDP-канал для каждого клиента и удаляет неактивные каналы.

Временный мост на прежнем узле может использовать тот же скрипт для сохранения
доступа по старому IP во время обновления DNS. Обычные TCP-сервисы, например
закрытый канал БД, настраиваются без добавления PROXY-заголовков.

Пример конфигурации входного моста:

```json
{
  "trusted_proxy_ips": [],
  "tcp": [{"bind": ["0.0.0.0", 25565], "target": ["127.0.0.1", 25566], "proxy_protocol": 1}],
  "udp": [{"bind": ["0.0.0.0", 19132], "target": ["127.0.0.1", 19133], "proxy_protocol": 2}]
}
```

Запуск: `python scripts/onix_game_proxy.py <config.json>`. В рабочем контуре
используется фоновая задача Windows с явным путём к Python. Поле
`required_marker` запрещает запуск до завершения восстановления данных.

Проверка протокола и реального трафика на временных локальных портах:

```powershell
python -m unittest discover -s tests -p test_onix_game_proxy.py -v
```

## Данные и откат

Перед запуском проверяются размер и SHA-256 архива, затем контрольные суммы
восстановленных файлов. БД сохраняется логически и физически при остановленных
писателях. Для окончательного переключения нужен финальный снимок БД, если
веб-API продолжал работать во время переноса миров.

Старый игровой контур и его CI не должны одновременно запускать вторую
записываемую копию миров. Исходные данные сохраняются для отката. После приёма
новых игроков откат требует сначала сохранить новые изменения целевого узла;
запуск устаревшей копии без этого потеряет прогресс.

Проверка реальной перезагрузки хоста проводится отдельно: успешный запуск
фоновой задачи на работающем Docker не равен проверке холодной загрузки.
